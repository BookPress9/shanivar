# Discipline Engine (App-Lock + Alarm) — Delivery Squad

Research base: `shanivar-vbt/discipline-engine/platform-research.md`. Product context: `android-app/PRODUCT_DIRECTION.md` ("Wake-up alarms", "Focus"), `android-app/NATIVE_HANDOFF.md` ("Native discipline seams to agree"). Founder-locked decisions (from the earlier VBT track): Android-first, alarm dismissal requires a physical/verified action, "non-dismissible" must be framed as "maximally inconvenient," never literally impossible.

## Staff Manager decision, 2026-09-10: dismissal methods
Two selectable dismissal methods for v1, both launched via the fastest possible path from the full-screen alarm activity straight to a camera screen (no app navigation in between):
1. **QR scan** (deterministic decode of a user-placed physical sticker away from bed).
2. **Photo + genuine motion** (new, in place of ML scene-matching): accelerometer must register real ambulatory motion between alarm fire and photo capture, combined with a photo being taken — deterministic threshold check, no fuzzy image-matching risk, no sticker required.
Rejected for v1: plain unverified photo snap (too easy to fake from bed), ML-based scene/reference-photo matching (real complexity/tuning risk for marginal gain over motion-sensing), puzzle-only (doesn't require leaving bed).

## Reconciliation (Staff Manager, 2026-09-10)
The two agents worked from the same documented contract but landed with real mismatches, caught during final verification rather than left for Codex to discover: backend requires the session id in the release path (`POST /focus/:id/release`) while the Kotlin client called a bare `/focus/release`; the client sent `package_names` where the backend expects `block_package_list`; `GET /focus/active` wraps its result as `{active: <row|null>}` not a flat object; dismissal recording needed `verification_detail` as a JSON object, not a string. Fixed directly in `DisciplineApi.kt`/`DisciplineEngine.kt` (added session-id tracking with re-discovery via `activeFocus()` if a process restart lost it locally) plus the two dismissal activities' recording calls. Also caught: the client was about to display `expires_at` (which includes a 30-minute staleness-cleanup grace period) as "time remaining" — fixed to compute the real intended end time from `started_at + requested_duration_minutes` instead. Rewrote `DisciplineEngineTest.kt` accordingly. Final state: 58 JVM unit tests passing, `assembleDebug`/`lintDebug` clean, no emulator involved.

Also discovered mid-reconciliation: Codex appears to be actively integrating the reflection scroller feature into these same native files concurrently (a "Reflect with Shanivar" button wired into `BlockOverlayActivity.kt`) — not a conflict with this work, but noted for awareness.

Founder decisions flagged, not guessed: focus-session duration bounds (5–480 min) and staleness grace period (30 min) are placeholder values from the Backend API Agent; actual paid-plan/pricing for the entitlement gate is undefined (the gate itself is real and wired to the existing `membership` column, but nobody is actually blocked today since there's no real plan to sell yet).

## Backend refinement + hardening, 2026-09-12
The delegated backend agent for this stalled with no progress (background-task watchdog killed it after 600s, before it got past reading files) — done directly instead rather than re-risk a second stall. Refinement: default block-list broadened from Instagram-only to six apps (added YouTube/TikTok/Facebook/X/Snapchat; TikTok's package id verified via web search since it doesn't contain "tiktok"), shipped as a live `ALTER TABLE ... SET DEFAULT` (a plain `CREATE TABLE IF NOT EXISTS` does nothing to a table that already exists, which these did) so it actually took effect on the live DB, confirmed by reading the column default back from `information_schema`. Added `GET /discipline/lock-targets`. Tightened `days_of_week` validation to reject an empty array (a schedule that can never fire on any day is a mistake to catch, not a valid state — `enabled: false` already covers "off").

Hardening: wrote and ran a live adversarial test script (two real registered accounts, real concurrent/cross-user requests against the running server, not mocks) covering the exact cases named in this squad's original scope. Found one real bug: `POST /focus/start`'s "already active" check was a SELECT-then-INSERT with no atomicity guarantee — two simultaneous start requests for the same account both returned 201, producing two active sessions at once. Fixed with a partial unique index (`focus_sessions_one_active_per_user_idx ... WHERE status = 'active'`) plus catching the resulting `23505` as a 409, mirroring the exact pattern `auth.js` already uses for the registration race. Re-ran the full adversarial suite after the fix: concurrent-start race, cross-user isolation (focus sessions and alarms, by ID guessing not just listing), entitlement-gate correctness (`free` vs `trial` membership), and the `days_of_week` edge cases all pass. Existing `discipline.test.js` unit suite (34 tests, mocked) still passes unchanged. Dismiss-endpoint self-abuse: confirmed no XP/streak is tied to `/alarms/dismiss` in this file, so a self-spammed fake dismissal only pollutes that user's own analytics — left un-rate-limited as a deliberate, low-risk call, not an oversight.
