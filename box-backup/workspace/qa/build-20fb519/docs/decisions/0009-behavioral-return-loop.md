# 0009 — Return for the next conscious choice, not engagement

- Date: 2026-09-18
- Status: Accepted by founder on 2026-09-19 for V1 product direction and wireframes; native implementation to be tracked separately
- Scope: behavioral model within the locked Alarm + Focus MVP

## Context

The founder defined Shanivar as a product of discipline, consciously better decisions, consistency and leaving an unwanted loop. Users need a meaningful reason to return, while the product's success can ultimately mean needing it less. Engagement mechanics that maximize app opens would conflict with that outcome.

## Decision

Use **Choose → Prepare → Protect → Notice → Review → Adjust → Leave** as the V1 behavioral loop.

The product returns at a user-selected alarm, a voluntarily started focus session, an attempted opening of a protected app, session completion and an optional weekly recalibration. The chosen activity should appear through the entire experience. Plans should be rendered as simple when-then commitments. Reviews should capture usefulness and one possible adjustment. A compact recent-choices card should show factual attempts and outcomes without streaks, ranks or scores.

Keep the approved alarm and focus engines unchanged in purpose. Add no AI coach, content feed, social comparison, family surveillance, predictive targeting or gamification to V1.

## Reason

This model aligns implementation intentions, autonomy support, decision-point friction, brief urge observation, progress monitoring, stable-context repetition, just-in-time support and compassionate reengagement after lapses. It provides a reason to return that serves the person's goal rather than Shanivar's engagement metrics.

## Evidence and limits

The research-to-product mapping, source links, copy and experiment plan are in [Shanivar V1 behavioral alignment](../../research/shanivar-behavioral-alignment-v1.md). Evidence from adjacent behaviors informs hypotheses; it does not demonstrate a Shanivar outcome.

## Implementation boundary

The founder approved the direction and asked for the V1 wireframe updates. The interactive prototype demonstrates the wording and feedback loop with simulated events. The native application must use actual alarm/focus outcomes before showing any counts; wireframes are not evidence of backend delivery. Preserve the locked Alarm + Focus tool set.
