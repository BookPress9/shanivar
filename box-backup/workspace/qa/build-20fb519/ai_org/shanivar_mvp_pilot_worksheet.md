# Shanivar initial pilot worksheet

Status: ready for an authorized pilot; no recruitment or results yet. Owner: product manager. Read the [PM review](product_manager_mvp_review_2026-09-13.md) and [scope](../android-app/INITIAL_MVP_SCOPE_2026-09-13.md).

Verify the build on physical hardware first. Begin with three willing parents introduced by adult children and three independent young adults. Count helpers separately. Complete Hindi review before Hindi-speaking recruitment. Fix blockers before prioritizing family acquisition learning; preserve the young-adult comparison. Small samples reveal problems, not efficacy or penetration estimates.

## Invitation drafts, not sent

Plain: “Would you like to try a short break from scrolling for something you choose? Shanivar can pause one distracting app for a little while. You choose when to start and stop.”

Optional Shani framing: “Shanivar offers a short practice inspired by Shani: choose what deserves your attention and protect a little time for it. Would you like to try it? The choice stays yours.”

Helper guide: ask first, explain whole-app blocking and duration, help where requested, then hand the phone back. Ask the parent to describe their own plan. Helpers receive no private activity report. Use a verified installation destination only during authorized recruitment; no referral system is needed.

## One record per participant

Use pilot IDs; omit private journal text and app contents. Record unknown and declined answers. These are research fields, not mandatory onboarding questions.

| Field | Record |
| --- | --- |
| Path | Parent introduced by adult child / young-adult self-use; helpers counted separately |
| Invitation | Delivered; plain or voluntarily chosen Shani framing; participant's own willingness or refusal |
| Language/device | Language understood, framing chosen, device eligibility, build version |
| Own goal | Chosen activity; whole-app versus feed-only need |
| Setup | Time, assistance, completion or account/network/permission failure |
| Local preview | Tried/skipped; understood it does not block apps? |
| Protection | Confirmed start, block behavior, expiry/release/failure; separate from self-report |
| Experience | Helpful/unhelpful/unknown and what happened to the chosen activity; optional |
| Repeat | Independently observed / voluntarily reported / needed help / did not repeat / unknown |
| Barrier | Motivation, remembering, language, setup, coverage, reliability or another stated reason |

## Decision rules

V1 now includes alarms and focus modes. Let each participant begin with the tool they want, and check both tools across the cohort. Add separate alarm fields: requested time/repeat days, native next occurrence, permission/sync failure, observed fire, dismissal/accessible method, edit/cancel, independent repeat and optional report of whether the alarm helped them begin. Alarm scheduling is not a focus start; dismissal does not prove getting out of bed. Measure time to correctly configured alarm separately from time to confirmed focus. Record device, assistance and language for both. School-age readiness is still unverified; the adult shakedown does not establish all-age fit.

Retain separate family counts: invitations delivered → parents independently interested → eligible devices → installs → setup completed → protected starts → voluntary repeats. Show raw counts and each preceding-stage denominator. Keep young-adult results separate using equivalent applicable stages. Helper interest is not parent activation; preview use is not protection; nonresponse is unknown.

Do not expand while any participant has an unmanaged service or misleading status. Provisionally seek two users per path independently repeating and explaining whether the session helped their activity. This is a management gate, not an efficacy benchmark. Record why it fails before adding reach.

For the next release, record the barrier, affected path and count, participant evidence, smallest change, owner, acceptance check and stop condition. Fix reliability or comprehension first. Test a lightweight reminder if valuable sessions are forgotten; reconsider auth only when account friction blocks use. If users require feed-only control, revisit feasibility and positioning before scaling. Later distinguish independence, useful ongoing support, dissatisfaction and unknown nonuse.
