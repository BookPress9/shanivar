## One offer, two practical starting points

**Pitch draft:** "Shanivar is being built to help you get up when you choose and protect time from distracting apps, with a brief pause to notice what matters."

Use present-tense feature claims only after release verification. The home should make **Set an alarm** and **Start focus** immediately recognizable. Let participants use either tool independently; do not require an alarm to begin focus, a focus session to use an alarm, or a reflection to finish either. Alarms provide a chosen time to act. Focus protects the activity. Awareness is a short optional layer within that useful routine.

Do not turn this into two brands, two onboarding funnels or a spiritual course. One familiar app can offer both tools without chart intake, a content feed or a conceptual lesson. Do not imply that an alarm schedules a future focus session unless that behavior is actually implemented and tested.

| Audience situation | Product implication | Acquisition hypothesis |
| --- | --- | --- |
| Parent wants time for reading, prayer, a walk or family | Familiar activity choices, readable controls, clear alarm time, participant confirmation | A respectful family invitation can help initial discovery |
| Younger self-user wants to begin study, work or creation | Fast direct setup; show chosen task and real remaining time | A concrete morning or study scene can outperform abstract self-improvement copy |
| Helper worries about a parent's scrolling | Explain the product, ask first, help only when requested, hand back the phone | Parent willingness and independent repeat matter more than helper enthusiasm |

The strongest acquisition message may differ by situation. Compare it; do not infer that all parents prefer faith or all younger people want productivity.

## Original interface copy for implementation

These are short English drafts. Translate the same meaning into Hindi and verify with a fluent reader before recruitment relying on Hindi. Actual controls, timing and permissions must match the engine. Accessibility applies to both alarm and focus flows, including large text, spoken labels and alternatives to physical alarm tasks.

| Surface | Suggested copy | Implementation note |
| --- | --- | --- |
| Welcome | "Make time for what matters." | Supporting line: "Set an alarm. Protect focused time. Notice what pulls you away." |
| Entry | "Start for myself" / "Help someone get started" | Helper guide can use parent examples; it is not a separate account type |
| Preview | "Try a one-minute pause" / "Skip" | Explicitly state: "This pause does not block apps." No signup needed |
| Pause | "Notice one sound. If you reach for your phone, notice the urge. You can choose what comes next." | No forced breath pattern, metaphysical reveal or agreement |
| Home | "Set an alarm" / "Start focus" | Two familiar actions; active alarm/session status remains visible |
| Alarm setup | "When do you want to get up?" | Show time and repeat selection clearly |
| Alarm confirmation | "Next alarm: [day], [time]" | Use actual next trigger including date/time changes; show setup problems instead of false confirmation |
| Alarm ringing | "Your alarm is ringing." | Primary control names the actual available action; use "Stop sound" only if that control truly silences it |
| Alarm task | "[Task] to finish" / "Use another way" | Match the chosen task; do not shame inability or require exercise for everyone |
| Intention | "What is this time for?" | Reading, study or work, prayer, a walk, family time, quiet time, or own activity |
| App selection | "Which apps do you want a break from?" | Match V1's supported selection count; explain whole-app coverage before start |
| Focus confirmation | "[Selected apps] will be blocked for [duration]." | No feed-only claim; do not suggest calls/messages within a selected app remain available |
| Active focus | "Time for [activity]. [Time] left." | Only when protection is confirmed active |
| Block surface | "You chose this time for [activity]." | "Return to my day" and optional "Take a short pause"; pause is not an unlock |
| Focus ending | "End focus?" | Explain the actual effect before the deliberate confirmation |
| Optional review | "Did this help you make time for [activity]?" | "Yes" / "A little" / "No" / "Skip"; then "Done" |
| Failure | "Protection did not start." | Follow with the real remedy; do not display a success timer |
| Helper guide | "Ask if they want to try. Explain what will happen. Help where needed, then hand the phone back." | Participant confirms their alarm or focus choices; no private helper report |
| Framing choice | "Choose your wording" | "Plain" / "Inspired by Shani"; discoverable secondary choice, changeable later |
| Shani explanation | "A practice inspired by Shani: choose your intention and act on it with patience." | Same utilities and neutral operational controls; no deity impersonation, punishment or requirement to believe |

Metacognition can be introduced later as "noticing how you think and changing your approach." It need not appear in onboarding. Do not rank intelligence, guarantee hyperfocus, promise dopamine repair or claim that boredom reliably produces insight.

## Fast learning before broad promotion

First verify alarms and focus on physical devices. Include alarm scheduling, ringing, silencing, task alternatives, editing/canceling and focus start/block/end/error behavior. Marketing should see the actual build and its supported-device limitations before preparing an availability claim.

Run the existing small adult usability shakedown with both family-introduced parents and independent younger adults. Ask each participant which tool solves a current problem, then let them start with it. Check both tools across the cohort without forcing everyone to use both daily. Record time to first correctly configured alarm separately from time to first confirmed protected session. An alarm firing is not proof that someone got up; a timer finishing is not proof they completed their chosen activity.

After usability blockers are resolved, prepare small, comparable acquisition tests:

| Question | Draft angle | Useful signal | Decision implication |
| --- | --- | --- | --- |
| Does a family introduction reach willing parents? | "Would you like help setting up an alarm or a short break from scrolling? You choose." | Invited parents who independently choose a tool, complete setup and repeat | Improve handback or setup before expanding family reach |
| Which job brings younger users in? | Morning: "Start the morning you planned." Focus: "Give one task your attention." | Comparable eligible visits -> chosen tool -> verified setup/start -> voluntary repeat | Lead with the useful job; retain both founder-mandated tools |
| Does Shani framing help willing participants? | Offer a plain and optional Shani explanation after stating the utility | Preference, accurate understanding and voluntary use; note self-selection | Improve discoverability if requested; do not claim causal uplift from self-selected groups |
| Does language block independent use? | Equivalent reviewed English/Hindi explanations | Comprehension, assistance and setup success by chosen language | Fix missing translation and readability before increasing recruitment |

Draft tests are not launched campaigns. Keep denominators, devices, source and observation window explicit. Small qualitative cohorts identify problems; they do not establish market penetration. Do not use helper enthusiasm, social views or longer app sessions as proxies for benefit.

## Claude V1 handoff requirements

1. Implement the approved alarm and focus scope with the shortest understandable paths; retain the optional awareness layer and participant-controlled framing.
2. Use original controls, strings and visual treatment. Competitor patterns can inform behavior; a competitor name does not replace a precise acceptance requirement or verified engine capability.
3. Keep deferred features out of the main navigation and onboarding. No astrology, AI scroller, family monitoring, payments, ranking or extra content library is needed to express this offer.
4. Validate comprehension of whole-app blocking, next alarm time, how to stop sound, how to deliberately end focus and what a helper can access. Users should explain these without memorizing an onboarding lesson.
5. Return the implemented flow, changed strings, verification evidence, remaining device or age-readiness limits and a short pitch walkthrough. Marketing then reconciles every claim to that build.

This handoff refines product direction and fixed copy. It does not mean a model has been trained or fine-tuned. Update the accepted learning log only when the owner records the founder decision or new comparable evidence; the current recommendation is not a performance finding.
