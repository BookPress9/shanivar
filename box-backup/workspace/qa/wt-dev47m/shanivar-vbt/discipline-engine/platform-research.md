# Discipline Engine — Android Platform Research & Feasibility

**Agent**: Discipline Engine Agent
**Track**: Shanivar VBT (parallel track, see `ai_org/shanivar_vbt_track.md`)
**Status**: Research complete, pre-implementation. No Kotlin/Java written in this pass.
**Scope**: (a) app-lockout during active practice sessions, first target = Instagram; (b) non-dismissible alarm requiring a physical/verified action (QR scan / puzzle / movement) to close — dismissal mechanism is a locked founder decision, not re-litigated here.

---

## Summary & Recommendation

Both features are buildable on Android today, but **only as a fully-native app** — `AccessibilityService`, `SYSTEM_ALERT_WINDOW` overlays, and full-screen alarm intents are not exposed through a Capacitor/WebView wrapper, so this directly constrains the App/UI Agent's shell decision toward native (or a native module bridged into a hybrid shell, which still means writing and maintaining real Android platform code either way). For app-lockout, build on **`UsageStatsManager`** (foreground-app polling, permission granted via Settings, no Play Store review flag) plus a **`SYSTEM_ALERT_WINDOW` overlay** to actually block the screen — this is the same combination shipping today in Play Store apps like AppBlock and Block. Do **not** make `AccessibilityService` the primary blocking mechanism: Google tightened this policy with a January 28, 2026 enforcement date restricting autonomous accessibility-API behavior to apps whose core purpose is assisting people with disabilities, and a March 2026 update further restricts accessibility API access under Advanced Protection Mode — an app-blocker is not a disability-accessibility tool and is now a real rejection/suspension risk on this API. For the alarm, use `AlarmManager.setExactAndAllowWhileIdle` (or `setAlarmClock` for the highest Doze exemption) plus a `Notification.Builder.setFullScreenIntent` full-screen activity — this is the same approach Alarmy and Google Clock use, but note Android 14+ restricts `USE_FULL_SCREEN_INTENT` to apps with a declared alarm/calling core purpose, which Shanivar can legitimately declare. **True non-dismissibility does not exist on Android without device-owner/enterprise MDM control** — a user can always force-stop the app or disable notifications from Settings; the founder-approved QR/puzzle/movement mechanism should be understood as "maximally inconvenient to bypass," not literally unclosable, and this framing needs explicit founder sign-off before build.

## App-Lockout: Options Compared

| Approach | Feasibility | Play Store Risk | Reliability |
|---|---|---|---|
| **`UsageStatsManager`** (foreground app detection) | High — standard API, permission granted via Settings > Special app access > Usage access (no runtime dialog, but no autonomous-flag scrutiny either) | Low — this is the established, policy-accepted mechanism for the entire existing "app/screen-time blocker" category (AppBlock, Block, Digital Wellbeing-adjacent apps) | Medium — polling-based, small detection latency (typically 1-2s), can be delayed by aggressive OEM battery management |
| **`AccessibilityService`** (foreground detection + intercept) | High technically, but Play Store now requires the "Permission Declaration Form" and restricts autonomous/rule-based use to apps whose **core purpose** is accessibility (`isAccessibilityTool="true"`); a discipline/focus app does not qualify | **High** — Google's Jan 28, 2026 enforcement date tightened this specifically against "convenience" uses like app-blocking that aren't disability-support tools; a March 2026 follow-up further blocks this API under Advanced Protection Mode. Existing app-blockers (e.g. AppBlock) now use Accessibility only as an *optional* enhancement (e.g. in-browser website blocking), not the core blocking mechanism | High when it works, but policy risk outweighs the reliability gain |
| **Device Admin / `DevicePolicyManager`** | Low for a consumer app — Google has been deprecating device-admin for enterprise use since Android 9/10; the modern replacement (Android Enterprise / Work Profile APIs) is scoped to MDM-managed devices, not consumer self-install | Low policy risk only because it's essentially unusable for this purpose — Play Store treats device-admin apps with suspicion, and users must explicitly and separately activate device admin, which is a poor consumer UX and does not achieve app-lockout on an unmanaged personal device | N/A — not a realistic path for a consumer app |
| **`SYSTEM_ALERT_WINDOW` overlay** (paired with UsageStatsManager, not standalone) | High — required companion to actually *block* the screen once the foreground app is detected (UsageStatsManager alone can only detect, not block) | Medium — overlay abuse (ad fraud, phishing, clickjacking) is a known enforcement area, but a transparent, disclosed, user-consented "this app blocks Instagram during your session" overlay is the established pattern for the entire app-blocker category and has not been targeted in the same way as accessibility misuse | Medium — Android 15+ requires the overlay to be actually visible to keep the permission meaningfully alive; some OEMs restrict overlay-drawing for battery-optimized/background apps |

**First blocking target: Instagram.** Justification: (1) it is the single most commonly named "doomscroll" app in user-research/founder framing for this product category, making it the highest-frequency user request to solve first; (2) it is easy to detect reliably via `UsageStatsManager` (single well-known package name, `com.instagram.android`, no need to disambiguate multiple sub-apps or browser tabs the way "social media" as a category would require); (3) it lets the MVP ship a narrow, provable v1 (one category, one app) before generalizing to a configurable block-list.

## Alarm: Options Compared

| Approach | Feasibility | Play Store Risk | Reliability |
|---|---|---|---|
| **`AlarmManager.setExactAndAllowWhileIdle`** | High — standard exact-alarm scheduling API, survives Doze reasonably well when combined with a foreground service at fire time | Low, if the app declares and is granted `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM` appropriately for its Android target level | Medium — "while idle" alarms are throttled/batched more than `setAlarmClock`; can fire a few minutes late under deep Doze |
| **`AlarmManager.setAlarmClock`** | High — the strongest Doze-exemption tier available to a non-privileged app; this is what real alarm-clock apps use | Low — Play Store explicitly recognizes "alarm" as one of the two core-functionality categories (with calling) that legitimately qualifies for full-screen-intent and exact-alarm allowances | High — closest to guaranteed on-time firing of any public API, still not immune to OEM-specific kill lists |
| **Full-screen intent** (`Notification.Builder.setFullScreenIntent` → wakes screen, launches full-screen Activity) | High — this is the correct, intended API for "alarm going off" UX | Low for Shanivar specifically, *if* the app declares alarm functionality as its core use during Play Console review: Android 14+ auto-revokes `USE_FULL_SCREEN_INTENT` by default for apps without a declared calling/alarm purpose, but grants it automatically to apps that do declare and qualify. Must complete the Play Console core-functionality declaration (required since May 31, 2024) | High once granted; user can still revoke the permission manually via Settings > Special app access, which the app should detect and warn about |
| **`SYSTEM_ALERT_WINDOW`** (used by Alarmy for the dismissal/mission screen, and to block power-off / "prevent turn off" style behavior) | Medium — works, but is a secondary/reinforcing layer on top of the full-screen intent activity, not a replacement for it | Medium — same overlay-abuse enforcement area as above; an alarm app using it for a legitimate, visible, user-expected purpose is an established pattern (Alarmy ships this today) but is not risk-free | Medium — some OEMs restrict overlay windows for background-optimized apps |
| **Device Admin** (to resist uninstall/force-stop) | Low — same enterprise-deprecation issue as above; Alarmy reportedly uses Device Admin narrowly to resist casual uninstall, but this does not prevent force-stop and carries the same policy exposure as any device-admin request from a consumer wellness app | Medium-High — asking a consumer user to grant device-admin rights for a "wake up app" is both a conversion-killing UX ask and a policy-scrutiny magnet | Partial — resists uninstall-while-active in some cases, does not resist Settings > Force stop |

**Physical/verified dismissal mechanism (QR scan / puzzle / movement)**: this is implemented as the full-screen Activity's *content*, not a new platform capability — once the full-screen intent has launched the Activity over the lock screen, the dismissal logic (camera-based QR scan via CameraX, accelerometer-based movement detection, or an in-app puzzle) is ordinary app logic gated behind that Activity refusing to finish() until the condition is met. The platform research finding here is that the *launch and stay-on-top* mechanism (full-screen intent + `SYSTEM_ALERT_WINDOW` + foreground service keeping the process alive) is the hard platform constraint; the verification step itself is not a platform limitation.

## Recommended Architecture

- **App-lockout v1 (Instagram)**: `UsageStatsManager` polling (foreground service or WorkManager-scheduled short-interval checks) to detect `com.instagram.android` in the foreground during an active session window → `SYSTEM_ALERT_WINDOW` overlay Activity to present the block screen and redirect the user back to the session. `PACKAGE_USAGE_STATS` is granted once via a Settings deep link (`ACTION_USAGE_ACCESS_SETTINGS`), not a runtime dialog — this needs clear onboarding copy since it's an unusual grant flow for users. Do not add `AccessibilityService` for v1; revisit only if a specific reliability gap (e.g. in-browser mobile-web Instagram access) demands it, and only after re-checking policy status at that time, since this is one of the fastest-moving policy areas on Android right now.
- **Alarm**: `AlarmManager.setAlarmClock` (preferred over `setExactAndAllowWhileIdle` for maximum Doze exemption) to schedule → fires a `Notification` with `setFullScreenIntent` targeting a dedicated full-screen "session alarm" Activity → Activity runs a foreground service to stay alive and keeps `SYSTEM_ALERT_WINDOW`-level presentation over the lock screen → dismissal gated on the founder-specified physical/verified action. Complete the Play Console core-functionality (alarm) declaration early, since it gates both the full-screen-intent auto-grant and exact-alarm scheduling on Android 14+/15+ targets.
- **Both features require a fully-native Android build** (Kotlin, targeting the platform APIs directly). This is the one finding that most directly constrains the App/UI Agent: these APIs are not accessible through a Capacitor/WebView shell in the way the rest of the app (onboarding, session player UI, content display) could be. A hybrid shell is not ruled out entirely — a WebView-based app *can* embed a native plugin/module that implements just this discipline-engine slice — but the founder and App/UI Agent should treat "discipline engine = native module, minimum" as a hard constraint on the shell architecture, not a nice-to-have.

## Flagged Limitations

- **True non-dismissible alarm is not achievable.** A user can always: force-stop the app from Settings > Apps > Force stop (which kills the foreground service and silences the alarm); disable the app's notification channel or all notifications; revoke `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM`/full-screen-intent permissions manually in Settings; or uninstall the app outright. None of these can be prevented without device-owner/enterprise MDM provisioning, which is not viable for a self-installed consumer app. The build target is "maximally inconvenient to bypass," not "impossible to bypass" — this framing must be explicit in any founder-facing or user-facing claim about the feature.
- **`AccessibilityService` is not viable as the primary or sole app-lockout mechanism** given the current Play Store enforcement posture (tightened access as of Jan 28, 2026, further restricted under Advanced Protection Mode as of the March 2026 update) unless Shanivar is willing to redesign the feature narrative around genuine accessibility support, which it is not.
- **OEM background-kill behavior (Samsung One UI "Sleeping Apps," Xiaomi MIUI autostart/background restrictions, and similar on OnePlus/Huawei) can silently break both features** — a scheduled alarm may not fire, or a foreground-service-based blocking check may be killed, on a meaningful share of real-world devices unless the user manually whitelists the app (battery optimization exemption, autostart permission). This needs onboarding UX (e.g. a "make sure your alarm works" setup flow linking to OEM-specific settings, following the pattern used by Alarmy and other alarm apps) and cannot be fully engineered around in code alone.
- **`UsageStatsManager`-based detection has inherent latency** (typically low single-digit seconds) between the user opening Instagram and the block overlay appearing — a brief flash of the blocked app is expected and should be treated as a known UX limitation, not a bug to chase to zero.
- **Full-screen-intent and overlay permissions are both manually revocable by the user** at any time via Settings > Special app access, independent of any in-app safeguard — the app can detect and warn about a revoked permission but cannot prevent the revocation.
- **iOS has no equivalent path** (Screen Time/Family Controls APIs cannot replicate true app-lockout or a non-dismissible alarm) — already captured as a locked decision in the track spec, restated here since it reinforces the Android-first, native-first framing.

## Open Questions for Founder

1. **Accessibility API stance**: given the Jan 28, 2026 Play Store enforcement tightening, do we commit to *never* using `AccessibilityService` for app-blocking (recommended), or is there appetite to revisit it later for reliability gaps (e.g. blocking Instagram access through a mobile browser) at the cost of real Play Store rejection/suspension risk? This should not be decided unilaterally by this agent given the "app gets removed from the Play Store isn't an MVP, it's a dead product" stakes.
2. **"Non-dismissible" framing in user-facing copy and marketing**: since true non-dismissibility doesn't exist on Android, what language is the founder comfortable with (e.g. "hard to skip" vs. implying literal impossibility)? This has product-honesty and potential consumer-protection-policy implications, not just an engineering nuance.
3. **Native vs. hybrid shell decision**: does the App/UI Agent's shell get built fully native given this constraint, or does it pursue a hybrid shell with a native discipline-engine module/plugin bridge? This finding should be handed to the App/UI Agent directly since it gates their architecture choice.
4. **Onboarding tolerance for unusual permission grants**: `PACKAGE_USAGE_STATS` (Settings deep link, not a runtime dialog), overlay permission, exact-alarm scheduling, and OEM-specific battery-optimization whitelisting all require multi-step manual setup outside the normal Android permission-dialog flow. How much onboarding friction is acceptable before a first practice session, given this is likely to cost some fraction of new-user activation?
5. **Second app-lockout target after Instagram**: once v1 ships, what's next — expand to a small fixed list (Instagram + TikTok + YouTube) or build a user-configurable block-list from day one? Affects whether `UsageStatsManager` polling needs to watch one package or an arbitrary set.
